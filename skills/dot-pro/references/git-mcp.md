# Compatible Git MCP delivery

This reference describes the five-tool contract of the Git MCP used for the verified delivery workflow. The server is not included in this skill. Obtain a compatible, user-approved endpoint and its authentication from the service owner; a placeholder such as `https://mcp.example.com/mcp` is not a working endpoint. Connect only when the task authorizes it, and confirm that the selected Pro conversation actually exposes the required tools.

For the ChatGPT connection procedure, see [OpenAI's custom MCP server guide](https://developers.openai.com/api/docs/guides/custom-mcp-server). Select the authentication configured for that service; do not assume every server uses `No authentication`. In ChatGPT, install and select the resulting plugin in the intended conversation. Follow current workspace permissions and write-confirmation prompts.

## Fixed version and tools

1. `project_context(project?, manifest_path?)` lists projects when `project` is omitted, or returns a project's fixed publication and current synchronization status. Omitting `manifest_path` selects its current fixed version. For a workspace task, supply its specified `<project>/v/<id>/manifest.json`. Retain the first chosen `manifest_path` and pass it explicitly to every later tool call; retain the same `account` and `task` for the delivery. Inspect `publication`, `git`, `task_defaults`, omissions and redactions, and read any needed project rules or manifest details. Start from the ready `publication.export_commit`; if current synchronization is blocked and the task requires the latest source, wait for it to recover.
2. `read_repository(project, manifest_path, path?, account?, task?)` lists a directory or reads a UTF-8 file from the fixed export commit. Supplying both `account` and `task` reads their already-bound task branch; supply both or neither.
3. `commit_files(project, manifest_path, account, task, message, files, resume_initialized_branch?)` creates one commit with a list of file operations. Each item has `operation` (`create`, `update`, or `delete`) and a repository-relative `path`; create/update require the complete UTF-8 `content`, and delete omits content. A path appears only once per commit. The service uses existing Gitea file SHA values for updates; do not independently calculate a digest. The first call initializes the task fork at the fixed export commit. Each account and task is one valid Git branch component.
4. `pull_request(project, manifest_path, account, task, title, body, draft?)` creates or updates the PR for that task branch against the manifest's base. `draft=true` uses a `[WIP]` title. The service adds the manifest, `publication.export_commit`, and `publication.source_kind` fields to the PR body; do not duplicate those field lines. Describe actual changes, checks and gaps, and link an existing Issue when relevant. The service checks for and reuses an existing branch PR; multiple existing PRs cause an error for inspection.
5. `get_delivery(project, manifest_path, account, task)` returns the task branch, fixed baseline, head, diff and associated PRs. If a write returns `unknown`, call this first and decide what to do from the observed state; never automatically repeat the write. If it returns `initialized`, confirm the original manifest and head before explicitly resuming `commit_files` with `resume_initialized_branch=true`. Before the first file commit, a branch at the same baseline cannot distinguish different manifests, so retain the originally selected manifest.

In this implementation, MCP uses the top-level `task_branch_prefix` returned by `project_context`, producing `bot/codex-azure-bot/<account>/<task>`, even if a legacy manifest retains `task_defaults.branch_prefix=bot/`. Direct CLI/Dot Git follows the manifest's original prefix. State the actual branch when handing between routes; identical account/task values need not identify the same branch. Continue an existing task on its actual branch and PR; do not overwrite or force-push it.

These tools do not manage Issues, run commands or tests, build, merge, or deploy. An Azure PR is a remote delivery, not proof of company receipt or release. Follow the task's rules for checks, acceptance and publication, and report the actions actually performed.
