# Compatible Git MCP delivery

This reference describes the compatible Git MCP contract for direct delivery, review and same-fork batch merging. The server is not included in this skill. Obtain an endpoint and its authentication from the user or service owner; a placeholder is not a working endpoint. Connect only when the task authorizes it, and confirm that the selected Pro conversation actually exposes the required tools. A previously verified delivery does not establish that a later review or merge was performed by Pro.

For the ChatGPT connection procedure, see [OpenAI's custom MCP server guide](https://developers.openai.com/api/docs/guides/custom-mcp-server). Select the authentication configured for that service; do not assume every server uses `No authentication`. In ChatGPT, install and select the resulting plugin in the intended conversation. Follow current workspace permissions and write-confirmation prompts.

After a server update, refresh the tool list in the installed ChatGPT plugin's details and confirm that the selected Pro conversation exposes `prepare_batch`, `review_pull_request`, and `merge_pull_request` before dispatching a batch. An existing connection or a successful server API call does not establish that the conversation has the new tools. If refresh or confirmation is unavailable, report the limit without claiming Pro completed a batch merge.

Git push permission on a task fork does not imply permission to mark a PR merged in Gitea. The service owner should configure the necessary merge capability only within the authorized task fork and branch rules, preserving the other existing rules, and ensure that the fork permits `manually-merged`. That method records a Git merge that has already landed; it does not replace independent review or necessary checks. Do not switch identities to bypass a permission denial. Inspect the actual state as described below and resume only the unfinished operation after the permission issue is resolved.

## Fixed version and tools

1. `project_context(project?, manifest_path?)` lists projects when `project` is omitted, or returns a project's fixed publication and current synchronization status. Omitting `manifest_path` selects its current fixed version. For a workspace task, supply its specified `<project>/v/<id>/manifest.json`. Retain the first chosen `manifest_path` and pass it explicitly to every later tool call; retain the same `account` and `task` for the delivery. Inspect `publication`, `git`, `task_defaults`, omissions and redactions, and read any needed project rules or manifest details. Start from the ready `publication.export_commit`; if current synchronization is blocked and the task requires the latest source, wait for it to recover.
2. `read_repository(project, manifest_path, path?, account?, task?, expected_head?)` lists a directory or reads a UTF-8 file from the fixed export commit. Supplying both `account` and `task` reads their already-bound task branch; supply both or neither. Provide `expected_head` to require the expected head for the read.
3. `commit_files(project, manifest_path, account, task, message, files, resume_initialized_branch?, expected_head?)` creates one commit with a list of file operations. Each item has `operation` (`create`, `update`, or `delete`) and a repository-relative `path`; create/update require the complete UTF-8 `content`, and delete omits content. A path appears only once per commit. The service handles the Git objects needed for updates; do not independently calculate a digest. The first call initializes the task fork at the fixed export commit. When `expected_head` is provided, the branch must exist and the service uses a lease to require the task head to match. Each account and task is one valid Git branch component.
4. `prepare_batch(project, manifest_path, batch_account, batch_task)` prepares a same-fork batch branch with an empty commit binding it to the fixed manifest. Retain its account/task, returned actual branch and head for child PRs and integration. If the branch exists, inspect it instead of overwriting it.
5. `pull_request(project, manifest_path, account, task, title, body, draft?, batch_account?, batch_task?)` creates or updates a child PR against the same-fork batch when both batch arguments are supplied. Omit both for a summary PR against the manifest's upstream base. `draft=true` uses a `[WIP]` title; a PR must be non-draft and its title must not mark it WIP/Draft before review or merge. The service adds the manifest, `publication.export_commit`, and `publication.source_kind` fields to the PR body; do not duplicate those field lines. Describe actual changes, checks and gaps, and link an existing Issue when relevant. The service checks for and reuses an existing branch PR; multiple existing PRs cause an error for inspection.
6. `get_delivery(project, manifest_path, account, task, batch_account?, batch_task?, since_head?)` returns the task branch, fixed baseline, current head/base, diff, associated PRs and comments; supply both batch arguments to select a same-fork child PR. `diff` compares the fixed export with head; `current_diff` compares the current target/head merge-base with head, as in a PR. For incremental review, `since_head` must be a previously reviewed commit on that task branch's first-parent history from the fixed baseline to the current head. The returned `changes_since` compares it to the current head; separately assess any change to the base. If a write returns `unknown`, query the same target first and decide what to do from the observed state; never automatically repeat the write. If it returns `initialized`, confirm the original manifest and head before explicitly resuming `commit_files` with `resume_initialized_branch=true`. Before the first file commit, a branch at the same baseline cannot distinguish different manifests, so retain the originally selected manifest.
7. `review_pull_request(project, manifest_path, account, task, expected_head, expected_base, reviewer, verdict, checks, batch_account?, batch_task?)` records a review of the precise head and base as a bot PR comment. `verdict` is `approve`, `request_changes`, or `comment`; `checks` describes the checks actually performed and any gaps. It returns the comment's `review_id`. Supply both batch arguments for a child PR or omit them for the summary PR. A later `request_changes` on the same inputs blocks the earlier approval. Gitea uses a shared bot and `reviewer` is a self-reported label, not a separate Gitea identity or independently authenticated approval. Independent review depends on the actual Pro sessions and assignment.
8. `merge_pull_request(project, manifest_path, account, task, batch_account, batch_task, review_id, expected_head, expected_base)` merges only a child PR into its same-fork batch. A mismatched review, head or base is rejected. The service performs a controlled Git merge with a base lease and then marks the Gitea PR; do not merge the upstream synchronization mirror. If the result is unknown, query `get_delivery` with the same child PR arguments. If it reports `landed_unrecorded`, inspect the merge commit, parents and review before deciding whether to resume PR marking with the original arguments; never repeat the actual Git merge. If Gitea denies permission to mark the PR, report the error and incomplete state; resume according to the observed state after the permission issue is resolved.

MCP uses the top-level `task_branch_prefix` returned by `project_context`. Direct CLI/Dot Git may follow a legacy manifest's original `task_defaults.branch_prefix`. State the actual branch when handing between routes; identical account/task values need not identify the same branch. Continue an existing task on its actual branch and PR; do not overwrite or force-push it.

These tools do not manage Issues, run arbitrary commands or tests, build, merge the upstream mirror, or deploy. An Azure PR is a remote delivery, not proof of company receipt or release. Keep the summary PR's approved review ID, manifest, head, base, actual checks and source metadata for the authorized local receipt process. Use the provider's local integration process only if it can enforce those exact inputs; otherwise report the missing capability. A controlled snapshot does not share company repository history: receive only the task delta, not a direct history merge. If the company baseline relevant to the task has changed, or receiving it requires protected paths or a manual port, return those changes to the cloud for review instead of reusing the old approval. Keep company credentials local. Follow project rules for acceptance and publication, and report the actions actually performed.
