# dot-pro

Coordinate ChatGPT web Pro, Dot and local Codex using the runtime's documented native browser or desktop-app APIs. Do not use the retired bridge plugin, a separate browser automation stack, or undocumented ChatGPT endpoints. Account availability and web features are observations, not guarantees. Codex owns task boundaries, verification and authorized integration.

Automatically consider this skill for projects using an approved source-reader manifest when web delegation advances the requested task, and for explicit Dot or ChatGPT website collaboration, review, Deep Research, images, or related browser diagnostics. A mention, inspection or edit of the skill does not dispatch work. A skill match does not itself authorize sending material, changing settings, writing a repository, merging or deploying.

For an authorized task, prefer ChatGPT web **6 xhigh (级高)** for simple or bounded work and **6 Pro** for substantial, long-running independent work. If 6 Pro is unavailable, use 6 xhigh when available and authorized. Verify the actual option in the selected conversation and report any limitation or fallback. The user's explicit model choice takes precedence.

When optimizing dot-pro itself, edit or assess the skill and read only the task history needed to identify the workflow problem; do not resume workers or audit project PRs unless requested. A skill edit does not itself establish that an integration works.

## Choose and bind the workers

Follow the user's chosen account, browser, conversation, model, execution path, task scope and disclosure limits. For multiple accounts, use the user's assignments or task context; confirm the actual account, selected model, connection and tab before submission. Give each worker a bounded assignment with its output, constraints, dependencies and completion condition. Reuse relevant conversations without duplicating work. Split independent tasks only when useful, give writers distinct branches or non-overlapping ownership, and serialize dependent changes. Before reassigning work, establish that its previous owner stopped writing or preserve its isolated branch for reconciliation.

Bind each action to its selected tab or desktop session and pair Dot with a web conversation only when their account/session matches. Use the runtime's documented browser controls and create a named task session before opening pages for a new Chrome task. Include any user-specified model preference in each Dot task or follow-up. Do not copy credentials or browser state, bypass login or security prompts, or silently substitute another model. Report unavailable accounts, tools or quota based on the actual visible state.

## Deliver authorized code work

When the user authorizes compatible Azure Git delivery and the selected web conversation has the Git MCP connected, prefer the selected model's direct path: select the fixed manifest, read relevant source and commit scoped UTF-8 changes on the task fork. The model alone does not establish a connection or write access. Read [Git MCP reference](references/git-mcp.md) for its tools, batch merge, manifest handling and recovery. The service and its URL must be supplied and approved by the user; this skill does not provide or deploy a backend.

Use Dot for tasks needing an actual execution environment, business checks, non-text changes, or an existing accepted long-running task. The described MCP supports controlled same-fork batch merges, but no arbitrary shell, test/build execution, Issue management, upstream merge or deployment. A PR or tool response is not proof of testing, company receipt or release.

For a requested completed code delivery, use this default path within the user's authorization:

1. Have cloud authors complete independent scoped implementations and a different web conversation review each author's actual changes. Return concrete findings to the original author for fixes; the reviewer checks fixes and remaining affected changes. Select a lead reviewer and a single Dot integrator from the available accounts, preserving the user's assignments and model routing. Use a reviewer conversation that did not author the implementation; if the lead conversation wrote or supplied that code, choose another available conversation. Independence concerns the authoring and review sessions, not separate Gitea users.
2. Have the integrator reconcile shared files and cumulative work without applying the same delta twice, then run necessary checks in the existing environment. An independent web conversation reviews the integration and later changes incrementally. Do not impose a fixed number of review rounds or repeat a full review without a reason.
3. Record an approval and actual checks for the precise child PR head and batch base, and actually merge each approved child into the same-fork batch. A changed head or base requires fresh review of affected changes. Open one batch summary PR to the fixed manifest's upstream base and obtain an approval for its exact current head and base, covering integration changes not already reviewed. Treat the upstream as a synchronization mirror and do not merge it through this flow.
4. Codex uses the available local company integration process to mechanically receive the approved summary delta, checking the fixed manifest, approval, exact head/base and actual result. If company PR creation and final merge are authorized and supported, complete them locally; do not re-review each cloud PR. Return complex code questions, conflicts, protected paths, manual ports and relevant company baseline changes to the cloud for work and review. Do not reuse an approval after its inputs change. Company credentials stay local.

Where an authorized small-model worker is already available, use it for routine, bounded local CLI receipt/status commands, website tracking, or straightforward relays of already-decided messages. Specify the exact account, conversation or tab, authorized message or status question, and constraints; serialize actions on the same tab. Keep substantive decisions with the selected web model or Codex. Do not start a separate orchestration solely for that routing. If the necessary batch or local receipt capability is missing, report the actual limitation rather than claiming the completed path ran.

If the selected conversation's connection or required tools are unavailable, report the precise limitation. If setup is authorized, connect the approved service; otherwise give the selected model the authorized source excerpts, paths and revision for a concrete patch, then have Dot apply, check and deliver it where authorized. If Pro itself is unavailable, use an available fallback only when authorized and report the model used. Keep consequential blockers and shared-interface questions in the same conversation with the actual error and current diff; do not repeat resolved questions or mandate an extra review.

Keep the owner, account/conversation, fixed baseline, actual branch and PR, dependencies and completion condition in the existing task context. The MCP and direct Git routes may use different branch prefixes for an older manifest; identify the actual branch when handing work between them. An existing Issue may be referenced in the PR body; use an authorized capable tool for any Issue management required by the task.

When Codex has already implemented work locally and the user authorizes an Azure relay, push only the task's committed delta to a distinct fork relay branch. Give Dot its actual branch, baseline, author and checks, then have Dot inspect and deliver it through its own task branch. Do not attribute the relay push or unexecuted checks to Dot, or disclose private material beyond the authorized scope.

## Observe, recover and report

Observe the actual target message and status. If a send or write has an uncertain outcome, inspect the original conversation or call `get_delivery` with the same project, fixed manifest, account and task before deciding whether to retry. Do not duplicate assignments, pushes or PRs. Use notifications where available and check at an appropriate interval, backing off when unchanged; report meaningful progress and actual blockers rather than unchanged status. Check the changed head, PR and bound review/merge results, and keep PR descriptions aligned with actual checks, dependencies and limitations.

Follow the task's authorization and current platform confirmation rules. If an automatic review denies an operation, report the operation and reason; do not rephrase or reroute the same denied action. Retry only after the relevant authorization, capability or inputs change. Do not invent checks, hashes, compatibility layers or other work beyond the requested result; normal Git object identifiers and HTTPS transport required by authorized delivery do not require a separate hash audit. Dot may continue a requested long-running task while Codex is offline only if the product accepts it. Scheduled or recurring tasks require a user request; verify the visible schedule.

## Other website workflows

- **Review and analysis:** provide only authorized context, keep the chosen conversation for follow-up, and compare findings with actual source and behavior. Review alone does not authorize edits.
- **Deep Research:** use the website's actual research mode, wait for its result, and return the available complete report and source links. Report missing access or citations rather than presenting ordinary chat as research.
- **Images:** use the website's image creation or editing flow, upload only authorized references, and retrieve the actual result originals with documented browser capabilities. Continue requested edits in the same conversation.
- **Diagnostics:** inspect the relevant visible account, model, connection, task state and error. Preserve the session and report the concrete blocker; do not install a browser, plugin or extra runtime without task authorization.
